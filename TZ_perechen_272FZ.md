# ТЗ: Сервис обработки перечня «нежелательных организаций» (272-ФЗ)

Техническое задание для реализации в Claude Code. Язык проекта — Dart/Flutter.

---

## 1. Цель и контекст

Минюст России публикует «Перечень иностранных и международных организаций, деятельность которых признана нежелательной на территории РФ» на странице:

`https://minjust.gov.ru/ru/pages/perechen-inostrannyh-i-mezhdunarodnyh-organizacij-deyatelnost-kotoryh-priznana-nezhelatelnoj-na-territorii-rossijskoj-federacii/`

Периодичность публикации не установлена. Нужен сервис, который:

1. Ежедневно (включая выходные и праздники) скачивает файл-первоисточник (xlsx) с сайта Минюста.
2. Определяет дату актуальности данных и сравнивает её с датой предыдущей скачанной версии.
3. При обнаружении новой версии преобразует первоисточник в целевой CSV-формат (для загрузки в CDI): мэппинг полей + разбор наименований организаций по правилам.
4. Отправляет ответственному email-уведомление с результатами (новая версия найдена / не найдена; сколько новых записей, сколько исключено).
5. Предоставляет веб-UI, где ответственный видит весь список, новые записи подсвечены, результаты авторазбора можно править вручную; ручные правки имеют приоритет и сохраняются для будущих версий файла; есть кнопка подтверждения «всё разобрано верно, грузить в CDI».
6. Выкладывает итоговый CSV в папку, откуда существующий скрипт забирает файл для загрузки в CDI. Если ответственный не подтвердил версию до контрольного времени — файл выкладывается по расписанию в том виде, как разобрался автоматически.

## 2. Архитектура и стек

Система из трёх частей в монорепозитории, всё на Dart:

| Компонент | Технология | Назначение |
|---|---|---|
| `packages/core` | чистый Dart | Модели, парсер xlsx, правила разбора наименований, конвертер в CSV, diff версий. Без зависимостей от Flutter — полностью покрывается unit-тестами. |
| `apps/server` | Dart (`shelf` + `shelf_router`, пакет `cron`) | Планировщик, загрузчик, БД, REST API, SMTP-уведомления, публикация в папку CDI. |
| `apps/ui` | Flutter Web | Интерфейс ответственного (просмотр, правки, подтверждение). Собирается в статику, раздаётся сервером. |

БД — SQLite (файл, пакет `sqlite3` или `drift`); строение схемы должно допускать миграцию на PostgreSQL. Развёртывание — системная служба на «чистой» ОС: комплект (скомпилированный сервер + собранный Flutter Web + справочники) ставится установщиком под Windows (задача планировщика от SYSTEM), Linux deb/rpm (systemd) и macOS (launchd). *Изменение относительно первоначального ТЗ: от Docker отказались, комплект должен ставиться без контейнера.* Часовой пояс всех расписаний и дат — `Europe/Moscow`, задать явно, не полагаясь на настройки хоста.

Рекомендуемая структура репозитория:

```
/packages/core/          # логика разбора и конвертации
/apps/server/            # сервис
/apps/ui/                # Flutter Web
/reference/              # эталонные файлы: export.xlsx, perechen_organizatsij_272_FZ_2025_03_03.csv
/scripts/                # сборка комплекта поставки: build.sh, build.ps1
/packaging/              # установка службы: linux (systemd, nfpm), windows, macos
```

Эталонные файлы (приложены к задаче) положить в `/reference/` и использовать в golden-тестах.

## 4. Целевой файл (выход)

Эталон: `reference/perechen_organizatsij_272_FZ_2025_03_03.csv`.

**Имя файла:** `perechen_organizatsij_272_FZ_YYYY_MM_DD.csv`, где `YYYY_MM_DD` — дата актуальности из ячейки A2 первоисточника (НЕ дата загрузки/публикации). Для эталонного export.xlsx имя было бы `perechen_organizatsij_272_FZ_2026_08_14.csv`.

**Формат (строго по эталону):**

- Кодировка: **Windows-1251** (cp1251), без BOM.
- Разделитель: `;`
- Конец строки: CRLF (`\r\n`), включая последнюю строку.
- Первая строка — заголовки; заголовок первой колонки **пустой** (строка начинается с `;`).
- Значения в эталоне не экранированы. Если значение содержит `;`, `"` или перевод строки — экранировать по RFC 4180 (обернуть в кавычки, кавычки удвоить) и залогировать warning (см. Р-6).
- Символы, отсутствующие в cp1251, заменять по правилу транслита/ближайшего аналога и логировать warning (напр. `ä` → `a`; в эталонных данных встречаются немецкие названия — проверить, что они конвертируются без потери смысла, иначе см. Р-6).

Колонки целевого файла (по порядку):

1. *(без заголовка)* — № п/п
2. Номер и дата распоряжения Минюста России о включении в перечень
3. Реквизиты решения Генеральной прокуратуры Российской Федерации о признании деятельности организации нежелательной
4. Наименование иностранной или международной неправительственной организации (рус)
5. Наименование иностранной или международной неправительственной организации (доп.)
6. Страна регистрации
7. Номер и дата распоряжения Минюста России об исключении из перечня
8. Реквизиты решения Генеральной прокуратуры Российской Федерации об отмене решения

## 6. Правила разбора реквизита «Наименование организации»

Сырая строка первоисточника разбирается на три целевых поля: `(рус)`, `(доп.)`, `Страна регистрации`. Правила (нумерация из постановки задачи):

1. Исключаем кавычки (`«»`, `""`, `''`, `„“`).
2. Исключаем скобки (сами символы скобок; содержимое скобок обрабатывается как отдельные кандидаты-наименования).
3. Часть наименования на кириллице → поле «(рус)», часть на латинице → поле «(доп.)».
4. При дублировании словосочетаний в наименовании — исключаем дублирование.
5. Русские слова, написанные латиницей (транслит, напр. `Otkrytaya Rossia`), → в «(доп.)», только если нет другого наименования на латинице; если есть — исключаем.
6. Иностранные слова, написанные кириллицей, → в «(рус)», только если нет другого наименования на кириллице; если есть — исключаем.
7. Страну из наименования → в «Страна регистрации».
8. Страну переносим из первоисточника **без преобразований** (как написано: `США`, `Соединенные Штаты Америки`, `Федеративная Республика Германия` и т.п.). Заложить страну отдельным полем, чтобы правило нормализации можно было добавить позже (Р-3).
9. Аббревиатуры наименования (напр. `EPDE`, `GMF`, `TRS`, `OR`) исключаем и не переносим.
10. Части наименования не на кириллице и не на латинице — исключаем (в текущем эталоне таких нет; если встретится как единственная часть наименования — записать в лог, поле оставить пустым, пометить запись «требует проверки», см. Р-4).
11. При наличии сходных наименований, оба на латинице (или оба на кириллице), — переносим наиболее длинное.

### 6.1. Рекомендуемый алгоритм

1. Токенизация строки на «кандидатов»: внешний текст до скобок; содержимое каждой пары скобок; внутри скобок и снаружи дополнительно делить по запятым верхнего уровня. Учитывать вложенные скобки и то, что страна может стоять и в скобках в конце (`(США)`), и после запятой в конце строки (`, Федеративная Республика Германия`).
2. Классификация каждого кандидата: `кириллица` / `латиница` / `страна` / `аббревиатура` (короткий токен из заглавных букв, обычно ≤ 6 символов, без пробелов или из инициалов) / `служебное` (напр. примечание вида `с 08.11.2017 – HUMAN RIGHTS PROJECT MANAGEMENT` — новое наименование после переименования: извлечь наименование, дату-примечание отбросить) / `мусор`.
3. Определение страны: сравнение кандидата со справочником стран (русские официальные и краткие названия: `США`, `Соединенные Штаты Америки`, `Великобритания`, `Федеративная Республика Германия`, `Литовская Республика`, `Итальянская Республика`, `Румыния` и т.д.). Справочник — редактируемый файл `packages/core/assets/countries_ru.txt`. Значение в целевое поле — исходная строка кандидата без изменений (правило 8).
4. Выбор итоговых значений: среди кириллических кандидатов — самый длинный (правило 11), с учётом правил 4–6; аналогично для латиницы. Дедупликация: кандидат исключается, если он является подстрокой (после нормализации регистра и пробелов) более длинного кандидата того же класса — напр. `Free Russia` при наличии `Free Russia Foundation`, `Atlantic council` при наличии `Atlantic council of the United States`, `Remembrance society` при наличии `The Remembrance Society`.
5. Очистка результата: убрать кавычки, лишние пробелы, висячие знаки препинания.
6. Каждой записи присваивается `confidence`: `ok` — разбор однозначный; `review` — сработали неоднозначные ветки (транслит, правило 10, несколько равнодлинных кандидатов, не найдена страна при наличии похожего на страну токена и т.п.). Записи `review` подсвечиваются в UI отдельно.

## 7. Процесс (end-to-end)

```
[cron: ежедневно, DOWNLOAD_CRON] 
   → скачать xlsx (ретраи) 
   → извлечь дату актуальности (A2)
   → дата <= даты последней версии?  → да: записать «новой версии нет», уведомление не слать (см. NOTIFY_ON_NO_CHANGES)
                                     → нет: создать Version
   → распарсить строки → авторазбор наименований (п. 6)
   → применить сохранённые ручные правки (п. 9)
   → diff с предыдущей версией: новые / исключённые / изменённые записи
   → сохранить в БД, статус Version = PENDING_REVIEW
   → email ответственному (п. 10) со ссылкой на UI
   → [ответственный в UI правит и жмёт «Подтвердить»] → статус CONFIRMED → публикация CSV в CDI-папку → PUBLISHED
   → [если не подтверждено к моменту AUTO_PUBLISH_CRON] → авто-публикация авторазбора → AUTO_PUBLISHED
```

Статусы версии: `DOWNLOADING → PARSED → PENDING_REVIEW → CONFIRMED | AUTO_PUBLISHED → PUBLISHED`, плюс `ERROR`.

## 8. Функциональные требования — сервер

### 8.1. FR-1. Загрузчик

- Запуск по cron (`DOWNLOAD_CRON`, по умолчанию `0 6 * * *` МСК) + ручной запуск из UI/API (`POST /api/jobs/check-now`).
- HTTP-клиент с таймаутом 60 с, до 3 попыток с экспоненциальной задержкой (1, 5, 15 мин). После исчерпания — событие `ERROR` + email об ошибке.
- Сохранять скачанный оригинал как есть: `data/downloads/export_{дата_актуальности}_{timestamp}.xlsx` (для аудита и переразбора).
- User-Agent и точный URL/способ получения ссылки — в конфиге.

### 8.2. FR-2. Определение версии

- Дата актуальности = значение A2 (datetime). Сравнение версий по этой дате (не по дате скачивания, не по хэшу).
- Дополнительно хранить SHA-256 файла: если дата не изменилась, но хэш другой — событие в лог и уведомление «файл изменился без смены даты актуальности» (пометить `review`).

### 8.3. FR-3. Идентичность записей и diff

- Ключ записи `org_key` = `{номер распоряжения о включении}__{дата включения в ISO}` (напр. `1076-р__2015-07-29`) — стабилен между версиями, в отличие от № п/п. При пустом номере — fallback: SHA-1 нормализованной сырой строки наименования.
- Diff новой версии с предыдущей по `org_key`: `new` (появились), `excluded` (исчезли из файла), `changed` (изменилась любая исходная колонка, в т.ч. сырое наименование).
- Исчезнувшие записи из целевого CSV не выдумывать: в CSV попадают только строки текущего первоисточника. Факт исчезновения фиксируется в БД и в уведомлении (см. Р-1). Если у строки первоисточника заполнены колонки исключения (7–9) или статус ≠ «Включена» — заполняются целевые колонки 7–8 по мэппингу.

### 8.4. FR-4. Ручные правки (приоритет человека)

- Правка хранится отдельно от авторазбора: `org_key`, поле (`рус` / `доп` / `страна` / прочие целевые), значение, автор, время, и `source_name_hash` — хэш сырого наименования на момент правки.
- При сборке версии: если для `org_key` есть правка и сырое наименование не изменилось — значение правки **перекрывает** авторазбор.
- Если сырое наименование изменилось — правка помечается `stale`, применяется авторазбор, запись получает `confidence = review` и попадает в список «требует проверки»; в UI stale-правка показывается рядом для сравнения.
- Полный аудит правок (история изменений не затирается).

### 8.5. FR-5. Генерация и публикация CSV

- Генерация файла строго по п. 4 (имя, cp1251, `;`, CRLF, порядок колонок, пустой первый заголовок).
- Публикация = атомарное копирование в `CDI_DROP_DIR` (запись во временный файл + rename), чтобы скрипт CDI не подхватил недописанный файл.
- Публикация происходит: (а) сразу по нажатию «Подтвердить» в UI; (б) по cron `AUTO_PUBLISH_CRON` (по умолчанию `0 20 * * *` МСК), если за день появилась версия в статусе `PENDING_REVIEW`. Повторная публикация той же версии — идемпотентна (перезапись файла с тем же именем допустима).
- Копия опубликованного файла — в `data/published/`.

### 8.6. FR-6. REST API (для Flutter UI)

```
GET  /api/versions                         — список версий (дата актуальности, статус, счётчики new/excluded/changed/review)
GET  /api/versions/{id}                    — карточка версии
GET  /api/versions/{id}/records?filter=    — записи версии; фильтры: all|new|changed|excluded|review|edited; поиск по подстроке
PATCH /api/records/{versionId}/{orgKey}    — сохранить ручную правку полей
POST /api/versions/{id}/confirm            — подтвердить и опубликовать
GET  /api/versions/{id}/export.csv         — скачать целевой CSV (предпросмотр)
POST /api/jobs/check-now                   — ручной запуск проверки сайта
GET  /api/health                           — статус сервиса, время последней проверки
```

Авторизация: минимум — Basic Auth (логин/пароль из конфига); сервис предполагается во внутреннем периметре (см. Р-7).

### 8.7. FR-7. Хранение (схема БД, ориентир)

- `versions(id, actuality_date, downloaded_at, file_sha256, source_path, status, counters_json, error_text)`
- `source_records(version_id, org_key, row_num, col1..col10 — сырые значения)`
- `parsed_records(version_id, org_key, target_no, incl_order, gp_decision, name_rus, name_add, country, excl_order, gp_cancel, confidence, is_new, is_changed)`
- `corrections(id, org_key, field, value, source_name_hash, author, created_at, is_stale)`
- `events(id, ts, type, payload_json)` — аудит: скачивания, ошибки, правки, подтверждения, публикации.

## 9. FR-8. Email-уведомления

SMTP-параметры и список получателей — в конфиге. Письма:

1. **Новая версия обнаружена** (основное): дата актуальности; итоги авторазбора — всего записей, новых, исключённых, изменённых, требующих проверки (`review`); список новых/исключённых организаций (кратко); прямая ссылка на экран версии в UI; дедлайн авто-публикации.
2. **Ошибка**: не скачалось после ретраев / не распознана структура файла — текст ошибки, ссылка на лог.
3. **Опционально** (`NOTIFY_ON_NO_CHANGES=false` по умолчанию): «проверка выполнена, новой версии нет».
4. **Авто-публикация выполнена без подтверждения** — уведомить, что ушла авторазобранная версия.

## 10. FR-9. UI (Flutter Web)

Три экрана:

**Экран 1. Версии.** Таблица версий: дата актуальности, дата скачивания, статус, счётчики (новые / исключённые / изменённые / review), действия (открыть, скачать CSV). Кнопка «Проверить сейчас». Индикатор здоровья сервиса (последняя проверка, следующий запуск).

**Экран 2. Версия (основной рабочий экран).**
- Таблица записей: № п/п, целевые поля (рус / доп / страна / реквизиты), бейджи `новая` / `изменена` / `review` / `правка вручную` / `stale-правка`.
- Фильтры: все / новые / изменённые / исключённые / требует проверки / с правками; поиск.
- Разворот строки: сырая строка первоисточника + как её разобрал автомат + текущие значения; редактирование целевых полей inline; кнопки «сохранить правку», «вернуть авторазбор».
- Ссылка из email открывает этот экран с предустановленным фильтром «новые».
- Кнопка **«Подтвердить и передать в CDI»** (с подтверждающим диалогом: имя файла, число записей). После подтверждения — статус и время публикации на экране.

**Экран 3. Журнал.** Лента событий (скачивания, ошибки, правки, публикации).

Требования: русскоязычный интерфейс; таблица должна комфортно работать на ~400–1000 строк (виртуализация/пагинация); отображение diff сырого наименования при `changed` (старое/новое).

## 12. Нефункциональные требования

- Логирование: структурированные логи (json), уровни; все внешние вызовы и ошибки — в `events`.
- Идемпотентность: повторный запуск проверки в тот же день не создаёт дублей версий.
- Надёжность: падение на любом шаге не должно оставлять полузаписанные файлы в `CDI_DROP_DIR` (атомарный rename) и полусозданные версии (транзакции).
- Переразбор: команда/эндпоинт для повторного прогона парсера по уже скачанному файлу (после доработки правил).
- Тесты: unit на все 11 правил (кейсы п. 6.2 обязательны), golden-тест конвейера, тест байтового формата CSV, тест приоритета правок и stale-логики, тест diff.

## 13. Этапы реализации (для Claude Code)

1. **M1 — `packages/core`**: модели; чтение xlsx (структура п. 3); разбор наименований (п. 6) с тест-кейсами п. 6.2; конвертер CSV (п. 4) с байтовым тестом; golden-тест на эталонных файлах из `/reference`. *Критерий: все тесты зелёные.*
2. **M2 — сервер, ядро**: БД и схема; загрузчик с ретраями; версия/diff; сохранение; cron. *Критерий: ручной запуск скачивает эталон (или локальный фикстур-файл), создаёт версию с корректными счётчиками.*
3. **M3 — публикация и почта**: генерация CSV из БД с учётом правок; атомарная публикация в `CDI_DROP_DIR`; авто-публикация по cron; SMTP-уведомления. *Критерий: e2e-сценарий «новая версия → письмо → авто-публикация» проходит на фикстурах.*
4. **M4 — REST API** (п. 8.6) + Basic Auth. *Критерий: интеграционные тесты API.*
5. **M5 — Flutter Web UI** (п. 10). *Критерий: полный сценарий ответственного — открыл из письма, отфильтровал новые, поправил запись, подтвердил, файл появился в папке.*
6. **M6 — комплект поставки, README**: сборка UI в статику и сервера в исполняемый файл, комплект с установщиком службы под каждую целевую ОС, документация по конфигу и эксплуатации. *Критерий: на чистой ОС установщик поднимает службу, `perechen paths` показывает корректные пути, `/api/health` отвечает.*

## 14. Решения по умолчанию (принято, разработку не блокируют)

Перечисленные ниже вопросы **не согласованы с заказчиком/вендором, но зафиксированы решениями по умолчанию**. Реализовывать сразу по ним — не ждать уточнений, M1–M6 идут в работу в полном объёме. Требование к коду: каждое решение вынесено либо в конфиг, либо в отдельную функцию/стратегию, чтобы смена поведения стоила одного изменения в одном месте и покрывалась параметризованным тестом.

| № | Вопрос | Решение по умолчанию | Точка изменения |
|---|---|---|---|
| Р-1 | Как отражать исключение из перечня (строка исчезает из файла или получает статус «Исключена») | В CSV попадают только строки текущего первоисточника. Если у строки заполнены колонки 7–9 или статус ≠ «Включена» — заполняются целевые колонки 7–8. Исчезнувшие строки в CSV не добавляются, фиксируются в БД (`excluded`) и в письме | `ExclusionPolicy` в `packages/core` |
| Р-2 | Формат реквизитов решения Генпрокуратуры | Только дата: `от 28.07.2015` (номера в первоисточнике нет). Исторические `№1 от…` из эталона не воспроизводим | `GP_DECISION_FORMAT=date_only\|with_number` |
| Р-3 | Нормализация страны (правило 8) | Страна пишется как в первоисточнике, без преобразований. Справочник только для распознавания, не для замены значения | `countries_ru.txt` + флаг `COUNTRY_NORMALIZE=false` |
| Р-4 | Наименование не на кириллице/латинице как единственная часть (правило 10) | Оба поля наименования пустые, запись `confidence = review`, сырая строка видна в UI | `NameParser`, ветка `other_script` |
| Р-5 | URL экспорта и недоступность сайта | URL из конфига; при отсутствии — парсинг страницы по селектору из конфига. Недоступность подряд > 3 суток → ежедневное письмо-эскалация | `MINJUST_EXPORT_URL`, `EXPORT_LINK_SELECTOR`, `UNAVAILABLE_ESCALATE_DAYS=3` |
| Р-6 | Тонкости CSV | Экранирование по RFC 4180 только при наличии `;`, `"` или переноса строки (+ warning). Символы вне cp1251 → транслитерация ближайшим аналогом (+ warning). Висячие пробелы из эталона считаем артефактом и не воспроизводим: значения `trim()`-аем | `CsvWriter` + `CSV_QUOTE_MODE`, `TRIM_VALUES=true` |
| Р-7 | Доступ к UI | Basic Auth из конфига, сервис во внутреннем периметре | middleware авторизации в `apps/server` |
| Р-8 | Кейс переименования (`с 08.11.2017 – HUMAN RIGHTS PROJECT MANAGEMENT`) | Целевым считаем новое наименование; старое отбрасывается; запись помечается `review` | `NameParser`, ветка `renamed` |

Все решения из таблицы отражать в README отдельным разделом «Принятые допущения» — чтобы при согласовании с заказчиком было видно, что именно менять.
